# Architecture decisions (ADR log)

Short, append-only log of decisions that are expensive to reverse. One entry per
decision: context, decision, consequences. New entries are added at the bottom.

## ADR-001 — Mobile renderer

**Status:** accepted (M0)

**Context:** the target is mid-range Android at 60 FPS in portrait. The project
does not need Forward+ features (SDFGI, volumetric fog, high-end screen-space
effects), and those features are expensive or unavailable on mobile GPUs.

**Decision:** use the `mobile` rendering method
(`rendering/renderer/rendering_method="mobile"`) and only mobile-safe
`canvas_item` shaders. Do not use Forward+-only rendering features.

**Consequences:** lower GPU cost and predictable mobile behaviour; any future
effect must be validated in the mobile renderer first. Desktop still runs the
same build, which is required for development.

## ADR-002 — 1080×1920 design space, `canvas_items` + `expand`

**Status:** accepted (M0)

**Context:** the game is portrait-only and must remain usable on 19.5:9 phones
and 4:3 tablets without stretching UI or battle art.

**Decision:** author the viewport at 1080×1920 with stretch mode `canvas_items`
and aspect `expand`, locked to portrait. Layouts anchor to the safe area, and
the battle field will letterbox its playable 1080×1480 region rather than
stretch.

**Consequences:** UI coordinates and art sizes are stable across devices; wider
or taller screens expose extra background area instead of scaling controls.
Every screen must be checked at both aspect extremes.

## ADR-003 — Data-driven resources

**Status:** accepted (M0)

**Context:** balance numbers, content definitions and localisation must change
without editing gameplay code, and the game must remain testable offline.

**Decision:** all content and balance values live in `.tres`/`.json` resources
under `res://data/` and `res://config/` (enemy/tower/unit stats, waves, maps,
upgrade curves, card effects, missions, localisation). Gameplay scripts read
those resources and contain no balance literals. Typed `Resource` classes are
the schema, with ids as `StringName`.

**Consequences:** designers can tune the game without code changes and headless
tests can load the same data. The cost is a data-loading layer and validation
tooling, which is built incrementally from M1.

## ADR-004 — Wave-clear cash bonus formula (M1)

**Status:** accepted (M1)

**Context:** spec §4.10 requires cash from wave clears, but only the skip bonus
(`10 + 2*wave`, capped at 120) has an explicit formula. The §13.4 banner example
("+120 cash") is illustrative, not a rule. The M1 acceptance list requires the
wave-clear bonus to be testable.

**Decision:** the clear bonus is `20 + 5*wave` for clearing wave `w`, authored as
`clear_bonus_base` / `clear_bonus_per_wave` on `WaveTable`. The skip bonus is
`min(10 + 2*wave, 120)` from the same resource. Both are data, not code.

**Consequences:** the banner amount is derived from data and covered by the smoke
test's cash delta; if the spec is later clarified, only the `.tres` changes.
Wave 5 therefore pays 45 cash; the 120 example would need a different curve.

## ADR-005 — Pause the simulation while the build sheet is open (M1)

**Status:** accepted (M1)

**Context:** spec §13.4 asks for a decision: bottom sheets and build modals
either pause the simulation and the wave timer, or let time run while shopping.

**Decision:** the build sheet pauses `BattleClock` (`paused = true`), which also
freezes the prep countdown and all battle systems. It never pauses the
`SceneTree`, so HUD tweens and input keep working. Closing the sheet resumes.

**Consequences:** no tower can be built while enemies advance, which matches the
M1 goal of a calm build phase. The Upgrade placeholder modal is informational and
does not pause.

## ADR-006 — Path2D drives logic, Line2D renders the road (M1)

**Status:** accepted (M1)

**Context:** §4.2/§11.2 require `Path2D` lanes as the source of enemy movement.
A `Path2D` only draws its curve in the editor; the runtime battle would show
enemies walking on invisible ground, making smoothness impossible to verify in a
screenshot.

**Decision:** each lane keeps a `Path2D` as the movement source and gets a sibling
`Line2D` sampled from the same `Curve2D` for rendering (brown road, 84 px wide).
The Line2D is generated by `BattleController`, never authored separately.

**Consequences:** one source of truth; the visual can never diverge from the
movement curve. Road width/colour are presentation constants, not balance data.

## ADR-007 — `TreeEntity` class name because `Tree` is native (M1)

**Status:** accepted (M1)

**Context:** Godot 4 already ships a native `Tree` Control class; a
`class_name Tree` fails to parse with "Class Tree hides a native class".

**Decision:** the entity's script class is `TreeEntity`; the scene node stays
named `Tree` and the spec-facing name in docs/UI remains "Tree".

**Consequences:** no collision with the engine class. References use the node
path `$Tree` plus the type `TreeEntity`.

## ADR-008 — M1 scope cuts: no selling and no tower sheet (M1)

**Status:** accepted (M1), superseded by ADR-014 (M2)

**Context:** the M1 brief requires a build sheet and a placeholder Upgrade
button, while `docs/milestones/M1.md` also lists tower selling. Both are
economy/upgrade-panel features.

**Decision:** M1 ships building only. `Tower.sell_value()` exists (70 % data
value) but no sell UI or transaction; tower sheets, upgrade tracks, speed control
and the pause menu stay in M3 per the M3 brief.

**Consequences:** no refund path to test yet; the build sheet is the only bottom
sheet. This is a deliberate vertical-slice cut, not an oversight.

## ADR-009 — Enemy pooling and a per-tick spatial hash (M2)

**Status:** accepted (M2)

**Context:** M2 acceptance is 120 concurrent enemies at >= 55 FPS with no
per-frame group scans, and the M1 `Tower._find_nearest_target()` walked
`get_nodes_in_group("enemies")` (including dead nodes) on every attack.

**Decision:** `BattleController` keeps a fixed pool of `Enemy` nodes, releases
them on death/leak instead of freeing, and rebuilds a `SpatialHash` from the owned
active array once per battle tick. Towers, units, the Tree, splash damage and the
aura pass query that grid. `EventBus.damage_dealt` is emitted by the controller
(not `Enemy`) so pure-logic tests can load `Enemy` without autoloads.

**Consequences:** no per-kill allocation, no group scans, and targeting is a
small candidate list. The grid is one frame stale (rebuild happens before child
`_physics_process`), which is <= ~2 px at runner speed and invisible in play.
Pooling requires every enemy reset in `setup()` and `release()`; a missed reset
would leak status/flash state into the next spawn.

## ADR-010 — Level curves and unit prices as shared data resources (M2)

**Status:** accepted (M2)

**Context:** spec 4.5 gives one tower formula (`base*0.8*1.55^(lvl-1)`, damage
x1.18, range x1.02, interval x0.97 floor 0.35) and the M2 brief adds a unit curve
(`50*1.45^(lvl-1)`). Unit placement costs are not specified.

**Decision:** `LevelCurve` resources hold max level, cost factor/growth,
per-level growth and the interval floor. Towers share
`data/levels/tower_levels.tres`; units share `data/levels/unit_levels.tres` with
`cost_base_override = 50` so every unit's upgrade curve is identical regardless of
placement price. Placement prices are authored per unit (50/90/70 cash) in
`UnitData.placement_cost`.

**Consequences:** a new tower/unit is data + a scene, and a balance pass touches
`.tres` only. The three placement prices are an M2 designer choice, not spec
numbers; record them in `BALANCE.md`.

## ADR-011 — Boss cadence lives on SpawnGroup, boss bar replaces the wave label (M2)

**Status:** accepted (M2)

**Context:** spec 4.8 wants "boss_troll with hp_mult from the table (e.g. wave 10:
x1.6 of scaled HP)" and a dedicated boss bar; §13.4 says the boss bar replaces the
wave bar while the boss is alive.

**Decision:** `SpawnGroup.hp_multiplier` carries the per-group boss multiplier
(1.6 in the wave table) and the Spawner passes it to the controller, so boss HP
stays authored data and the rest of the wave keeps its normal scaling. The HUD
shows `BossBar` and hides `WaveLabel` on `boss_spawned`, restoring it on
`boss_removed`. The wave table remains the only place that decides which wave is
a boss; `WaveManager` has no boss rules.

**Consequences:** wave 10 is 1 boss + 17 supports with one 1.6x group; the boss
group can be tuned without touching wave scaling. `debug_start_wave()` exists for
tools/tests to jump to a boss wave.

## ADR-012 — Behaviors are strategies selected by data id, shared by towers and units (M2)

**Status:** accepted (M2)

**Context:** the brief forbids `if tower_id == ...` chains and requires a
level-5 `TowerBehavior` registry. Units use the same combat pipeline and may need
behaviors later.

**Decision:** `TowerData.behavior_id`/`UnitData.behavior_id` name a strategy in
`TowerBehaviorRegistry`. Strategies receive `behavior_params` (a data Dictionary),
the level and the shot/aura dictionary, so one behavior works for any tower or unit
and all numbers stay in `.tres`. Behaviors are only instantiated at
`level >= unlock_level`.

**Consequences:** adding a behavior is one script + one registry entry, and its
power is tunable per tower in data. Unknown ids fall back to null (base behavior)
instead of crashing content loads.

## ADR-013 — M2 draw-call target deferred to the art/atlas pass (M2 deviation)

**Status:** accepted (M2), follow-up in M5/M8

**Context:** `docs/milestones/M2.md` targets < 120 draw calls at 120 enemies.
Placeholder enemy art is one texture per walk frame (6-8 files per enemy) and each
enemy also draws a shadow and an HP bar, so the measured peak is 532 draw calls
while FPS is far above the 55 floor (1945.9 FPS on desktop, vsync off).

**Decision:** ship M2 with measured numbers recorded; do not hide entities to game
the metric. Batch/atlas work belongs with the art pipeline (one atlas per screen
family is already spec 14.3) and is scheduled for M5/M8.

**Consequences:** the FPS acceptance is met on desktop, the draw-call acceptance is
not. LDPlayer FPS is unmeasurable until the M6 Android export, so mobile
performance remains an M6 gate.

## ADR-014 — M2 delivers the tower/unit sheets and selling (M2)

**Status:** accepted (M2)

**Context:** ADR-008 deferred tower sheets and selling to M3, but the M2 brief
explicitly requires build/upgrade/sell UI, unit placement and in-run unit
upgrades.

**Decision:** M2 implements the tower sheet (level, stat preview, upgrade, sell at
70 %), the unit sheet (placement + L1-10 upgrade) and keeps the tree upgrade panel
placeholder for M3. The old 540-line `BattleController` is split into state/flow +
`BattleHudController`, `BuildSheet`, `TowerSheet`, `UnitSlots`.

**Consequences:** ADR-008's cuts are closed for towers/units; M3 is now tree
upgrades, speed control, pause menu and the reward bundle. Sheets pause the battle
clock (ADR-005 still applies).


## ADR-015 — RunWallet + SpendResult as the only in-run cash mutation point (M3)

**Status:** accepted (M3)

**Context:** M2 wrote `RunState.cash` from `add_cash()`/`spend_cash()` and read the
autoload directly from build options. Spec 4.10 requires hold-to-buy that cannot
double-spend and a disabled reason, which a bare bool cannot express.

**Decision:** `RunWallet` (RefCounted) owns the balance, exposes `add()` /
`try_spend()` and returns a typed `SpendResult` (OK / INSUFFICIENT_FUNDS /
MAX_LEVEL / INVALID_AMOUNT + reason key). `BattleController` mirrors the balance
into `RunState.cash` inside one `_sync_cash()` method; nothing else writes cash.
Hold-to-buy drives `HoldToBuy.tick(delta, attempt)` and stops on the first failed
result, so a press can never buy past the balance.

**Consequences:** all purchase paths share one guard and tests can assert failure
codes; a future WalletService can replace the mirror without touching UI code.
`RunState.cash` remains for read-only consumers.

## ADR-016 — RewardBundle + RewardLedger grant run rewards once (M3)

**Status:** accepted (M3)

**Context:** spec 6.1 wants every reward source to be a `RewardBundle`, and a
summary can be re-shown after a reload/retry without paying twice. WalletService
does not exist until M4.

**Decision:** `RewardBundle` is the only reward payload (`coins/gems/stones/cash/
xp/cards`) and has a pure `apply_to(wallet, player)` with an amount > 0 guard.
`RewardLedger` claims run ids (last 50) and `GameState.claim_run_reward()` gates
the grant; `RunSummary` builds one bundle for the run and a coins-only bundle for
the rewarded double. `GameState.grant_bundle()` is the temporary meta-wallet
mutation point and logs the last 50 grants for support.

**Consequences:** mission/ad/IAP rewards can reuse the same path, and replaying a
summary never double-pays (verified by the battle smoke). M4 moves the mutation
point to WalletService and keeps the bundle/ledger shape.

## ADR-017 — Speed is a BattleClock delta multiplier, unlocks are data flags (M3)

**Status:** accepted (M3)

**Context:** spec 4.11 requires 1x/1.5x/2x with locked segments, and forbids
`Engine.time_scale` because UI tweens and audio pitch must stay real-time. Player
levels that grant 1.5x/2x are an M4 system.

**Decision:** `BattleClock.scaled(delta)` multiplies every battle system's delta,
so speed never touches the SceneTree clock or audio. Unlocks live in
`GameState.unlocks` (`speed_1_5`, `speed_2`) with level-3/10 fallbacks; locked
segments open a popup whose debug-build confirm button grants the flag via
`BattleController.debug_unlock_speed()`. Pause uses the same clock so spawning and
wave timers freeze while the HUD keeps processing (`PROCESS_MODE_ALWAYS`).

**Consequences:** speed cannot desync waves (battle smoke measures 2x elapsed and
monotonic waves), and QA can exercise both speeds before M4 levels exist. The
debug unlock is compiled out of behaviour in release builds.

## ADR-018 — Upgrade tracks are discovered from a directory (M3)

**Status:** accepted (M3)

**Context:** spec 4.10 requires the Tree upgrade panel to be generated from
`res://data/tree/upgrades/*.tres` so a new stat is a data-only change.

**Decision:** `TreeUpgrades.load_tracks()` scans the directory, sorts by the
resource's `order` then id, and `TreeEntity` reads aggregated bonuses by stat id
(`damage`, `attack_speed`, `crit_chance`, `crit_damage`, `range`, `regen`). Adding
a track is a `.tres` plus (if it is a brand-new stat) one read in `TreeEntity`;
the panel, costs and previews need no code. An optional `upgrade_tracks` export
on `BattleController` overrides the scan for tests/tools.

**Consequences:** content can add rows without UI edits; a typo in a stat id
silently contributes no bonus, so the data test asserts the six shipped ids.

## ADR-019 — M3 balance gate recorded as unmet (M3 deviation)

**Status:** accepted (M3), **superseded by ADR-021 (M3.1)**

**Context:** `docs/milestones/M3.md` accepts "a skilled manual run reaches wave
15+". The spec's own wave scaling (1.16 HP per wave, 6+1.2w enemies, 1800 HP boss
at wave 10) and base economy (starting cash 50, archer 60) leave roughly 50-70 DPS
by wave 4. Human play was not possible in this session; the automated probe dies
on wave 5 with three different openings (4, 3, 4 cleared waves).

**Decision:** do not fake the acceptance. Ship the M3 feature set, record the
measured probe numbers in `BALANCE.md` and the deviation in `PROGRESS.md`, and
schedule the wave/economy rebalance as an M8 task (or the first task of a short
M2.1 balance pass). No balance data was altered to make the number look green.

**Consequences:** the M3 tag marks the implemented feature scope, not a verified
wave-15 run. Any claim of wave 15+ must wait for a rebalanced wave table and a
human/recorded playtest.

## ADR-020 — Starting cash is 120, not the spec's 50 (M3.1)

**Status:** accepted (M3.1); spec §4.10 updated

**Context:** spec §4.10 said "starting cash 50" while §4.5 prices the cheapest
tower (Archer) at 60. A zero-meta player could not build before the first kills,
so wave 1 leaked by design and the run entered a death spiral. The M3.1 brief
explicitly allows fixing the data and the spec value.

**Decision:** `WaveTable.starting_cash = 120` (two archers or one archer plus a
unit/upgrade). The value is authored in `data/waves/wave_table_m2.tres` and the
`WaveTable` defaults; `docs/AI_BUILD_PROMPT.md` §4.10 now says 120 with this ADR
reference. `balance_probe.gd` and the unit tests assert it.

**Consequences:** wave 1 is playable and the opening choice is real (two cheap
towers vs one tower plus an upgrade). The number is data, so a later pass can
retune it without touching code. The M3.1 probe distribution (median 9, range
9-11) is measured with 120.

## ADR-021 — M3.1 balance pass: ranges, wave pressure and cash pacing (M3.1)

**Status:** accepted (M3.1)

**Context:** ADR-019 recorded that spec-conformant numbers cleared only 4 waves
(median) and died on wave 5. Root causes measured with the probe: (1) starting
cash below the cheapest tower, (2) 300 px tower range covering only a short arc of
the 859 px lanes, (3) `1.16^(w-1)` HP with 6+1.2w enemies and a x1.6 boss making
wave 10 ~11k HP against ~70 DPS, (4) kill cash `1.09^(w-1)` and a 20+5w clear
bonus too small for the 1.55 upgrade growth.

**Decision:** tune data only (no gameplay code):
- tower ranges: archer 300→400, cannon 280→370, frost spire 260→340 (spec §4.5
  values remain the design target; data is the launch source of truth);
- wave HP growth 1.16→1.11, counts 6+1.2w→5+0.8w, boss group x1.6→x1.20, spawn
  interval 0.72/0.35→1.00/0.45 s;
- economy: starting cash 120 (ADR-020), clear bonus 20+5w→60+14w, kill cash
  multiplier 1.09→1.12;
- probe heuristics: `fill`/`four`/`two` openings spend on the cheapest tower
  upgrade after the opening (only the `tree` opening buys Tree tracks), and the
  probe now reports damage share, per-wave peak enemies, seeds and exit status.

**Measured result:** 18 runs (3 openings × 6 seeds) with the final data: `fill`
11,11,10,10,10,10; `four` 9×6; `two` 9×6. Overall median 9, min 9, max 11, peak
11 concurrent enemies, all runs end in defeat (waves 10–12) and exit 0. Before the
pass the same probe cleared 4 waves and died on 5. Full table in `BALANCE.md`.

**Consequences:** a zero-meta run now lands in the spec's 8–12 window and earns
coins for M4; the game is no longer a wave-5 wall. This deliberately deviates from
spec §4.5/§4.8 numbers, so the spec tables are not rewritten beyond the explicitly
requested §4.10 starting-cash fix; `BALANCE.md` mirrors the launch data. If a
later design pass wants the spec numbers back, only the `.tres` files change.

## ADR-022 — Save schema v2 keeps the v1 filename and adds a checksum (M4a)

**Status:** accepted (M4a)

**Context:** M3 shipped a small `schema_version: 1` payload (player, wallet,
unlocks, wallet log) with an atomic write and `.bak`, but no checksum and no
sections for the M4 systems. Spec 8.2 requires a checksum, a full document and a
`migrate()` with a test per version step. Renaming the file would orphan every
M3 save, and the player ID is a UUID that must survive.

**Decision:** keep the paths `user://save_v1.json` / `.bak` / `.tmp` (the `v1`
is a historical filename, not the schema number) and bump the in-file schema to
**2**. The document contains every spec 8.2 section plus two local extras:
`is_onboarded` (first-launch state from 8.3) and `applied_rewards` (the run-id
reward ledger; without it a crash after a summary could pay twice). The
transaction log stays in memory only — it is support/debug data, not progress.
`migrate_v1_to_v2()` is a pure static function (input not mutated); v1's
`player.best_wave` moves to `stats.best_wave`, the v1 unlock dictionary becomes a
sorted id array, and missing sections are filled with spec defaults. The checksum
is SHA-256 over a canonical JSON (whole floats normalised to ints so a JSON
round-trip hashes identically) with the `checksum` field excluded. Settings are
mirrored into the document but `settings.cfg` remains authoritative on load,
because it is written by the live sliders before any save flush.

**Consequences:** M3 saves load and upgrade transparently, with one
`save_migrated v1 -> v2` log and an immediate v2 write. A corrupt main file (bad
JSON or checksum mismatch) loads `.bak` and sets `recovered_from_backup`; when
both fail the game starts a fresh profile instead of crashing. Any future schema
change adds a `migrate_vN_to_vN+1` function and a test, and the filename stays as
is unless a full reset is intended.

## ADR-023 — One ModifierService source per meta system (M4a)

**Status:** accepted (M4a); applies to cards/magica in M4b

**Context:** M3's `TreeEntity` applied in-run Tree bonuses internally and
`ModifierService` existed but was unused. M4 adds workshop (24 tracks), then
cards and Magica; the milestone's watch-out is "one aggregation point — if a stat
is modified in two places, the milestone failed".

**Decision:** every permanent system (workshop now, cards/magica later) registers
one source id in `ModifierService` (`&"workshop"`), and in-run Tree tracks are
published as a run-scoped source (`&"run_tree_upgrades"`) by
`BattleController._apply_run_modifiers()`. Entities never read a second bonus
dictionary: Tree, Tower and Unit ask `ModifierService.get_stat(stat, base)` for
damage, attack speed, crit chance/damage, range, regen, max HP, starting cash,
shield and reductions; cash/coin/XP/discount are read at the run/reward edges.
Tracks declared `mul` register `{mul: total}`, `add` tracks register
`{add: total}`, so additive stacking and multiplicative stacking both stay
explicit in data. Caps (crit 60 %, damage reduction 60 %, card drop 15 %,
track caps) are enforced at the resource and read site with `get_stat_clamped`.
`BattleController._exit_tree()` removes its run source so a run cannot leak
bonuses into the menu or the next run.

**Consequences:** adding a meta stat is a `.tres` plus one read site, and a test
can register a fake source without a battle. The trade-off is that a stat with a
meaningful base (e.g. attack speed as a multiplier) must pass a sensible base
(1.0) rather than 0, and run-scoped sources must be cleaned up by their owner.
Cards and Magica must use `add_source`/`remove_source` and never mutate stats
directly; if a future system needs per-frame values, it registers the source
again instead of caching a second aggregation.

## ADR-024 — Magica research uses UTC timestamps and a claim step (M4b)

**Status:** accepted (M4b)

**Context:** spec §6.4 requires real-time research that continues while the app is
closed, one active research, a 50 % cancel refund and a "Research complete"
badge. A save can be offline for weeks, so a countdown based on monotonic timers
would be wrong. Two behaviours were ambiguous: whether the effect applies the
instant `ends_at` passes, and how a second research slot would fit later.

**Decision:** store `research = {node_id, started_at, ends_at}` as UTC unix
seconds and derive everything from `TimeService.now_unix()`. `reconcile()` runs on
boot, on app focus/pause and on the screen tick; when `now >= ends_at` it moves the
node id to a saved `pending_claim` field and clears the active research. The
node's effects are published to `ModifierService` only after the player taps
Claim, so the badge cannot be missed while offline. `cancel()` refunds
`floor(cost * 0.5)` for coins and gems through `WalletService` and clears the
research. The research-speed modifier (`magica_speed`, shared with the workshop
track) is applied when research starts, not while it runs, so the shown duration
matches the stored `ends_at`. Each completed node registers its own
`magica:<id>` source, which keeps additive and multiplicative stacking explicit.
`pending_claim` is a local extra inside the existing v2 `magica` section.

**Consequences:** an app kill/restart is indistinguishable from a normal tick, and
a test can move `TimeService.override_unix` instead of waiting. A finished
research occupies the "one active research" slot until claimed, which is
deliberate (the player chooses when to acknowledge it). Adding a premium second
slot later is a `research` array migration, not a rewrite.

## ADR-025 — Card levels scale effect values, duplicates become shards (M4b)

**Status:** accepted (M4b)

**Context:** spec §6.5 fixes rarities, levels 1–5, the shard costs
(20/40/80/160) and the 12 launch cards, but not how a card level changes its
effect. Duplicates and the manual Upgrade button both spend the same shard
currency, so one rule has to cover both.

**Decision:** each `ModifierData` on a `CardData` is authored at level 1 and scaled
by `1 + 0.25 * (level - 1)` (level 5 = ×2.0). A duplicate grants 20 shards and
auto-upgrades while the next-level cost is affordable; the Upgrade button performs
one level-up from the same shard pool. The loadout is published as a single
`&"cards"` source built with `ModifierBuilder`, which sums `add`/`mul` parts per
stat before `ModifierService` sees them, so two copies of one stat on a card (or
two cards touching one stat) cannot overwrite each other. Slots are counted from
`UnlockService` (`card_slot_1..4`) plus the `card_slot_bonus` modifier (Deep Roots);
the save still writes four slots until the fifth is actually used, keeping old v2
documents byte-compatible.

**Consequences:** every card has a predictable power curve and a duplicate is
always useful; a card that adds a unit slot can reach +2 at level 5, which is
harmless because the map has four physical slots and the unlock check is `>= 1`.
The ×2.0 ceiling is a balance number, documented in `BALANCE.md`; if M8 wants a
different curve, only `CardData.LEVEL_STEP` and the doc change.

## ADR-026 — Missions are generated instances, not live template queries (M4b)

**Status:** accepted (M4b)

**Context:** spec §6.6 needs 3 daily + 5 weekly missions, scaling targets, a
04:00 local reset, claim-once rewards and completion bonuses. The device clock can
change timezone or jump; the app may be closed across several resets.

**Decision:** `MissionSchedule` is a pure helper over `now_unix` plus a UTC offset
in minutes. A mission cycle id is the shifted local date (`2026-10-31`, day starts
at 04:00) or ISO week (`2026-W44`, week starts Monday 04:00). `MissionModel.setup()`
compares the saved ids with the current ones and regenerates on mismatch, which
also clears progress, claims and the bonus flags. Generated missions are stored as
instances (`id`, template id, title, metric, mode, target, progress, claimed,
reward amounts), so a later template edit cannot invalidate an in-progress
mission. Targets scale `+12 %` per player level and rewards `+8 %` per level;
`mission_reward_bonus` from the workshop multiplies the claim. Rewards are paid
with `RewardBundle` through `GameState.grant_bundle` (which delegates to
`WalletService`), and `claimed` is set before any grant, so a double tap cannot
pay twice. The all-3/all-5 bonus is auto-granted exactly once when the last mission
is claimed; the weekly bonus also grants a random card through `CardService`.

**Consequences:** resetting across a 04:00 boundary is a pure id comparison and is
tested with simulated timestamps; no mission ever asks for premium currency. A
clock that moves backwards only causes an extra reroll, never a duplicate claim.
The bonus flags and `pending` sections are local extras in the v2 document.



## ADR-027 — Translation keys in scenes, LocaleService only in code (M5a)

**Status:** accepted (M5a)

**Context:** spec §10 requires one `strings.csv`, keys in `.tscn` labels instead
of literals, `LocaleService` formatting/plurals, instant switching and a
pseudo-locale for layout stress. Godot already re-translates a `Control.text`
that exactly matches a key when the locale changes, while values built in code
(e.g. `"Wave %d"` plus a number) cannot be translated by the engine.

**Decision:** static labels store the key as `text` and rely on engine
`tr()`/`auto_translate_mode`; every dynamic string calls
`LocaleService.t(key, fallback)`. Screens that build rows in code connect
`LocaleService.language_changed` and rebuild, so a switch is complete without a
scene reload. Formatting and plural rules live in the pure `LocaleFormat`
helper (unit-testable), with `LocaleService` as the autoload façade. Plural
catalogues use `.one/.few/.many/.other`; English uses `.one`/`.other`, Ukrainian
implements the 11–14 exception. `pseudo` doubles vowels and appends `…`; the
+60 % layout stress is captured through `tools/capture_scene.gd` because engine
auto-translated labels bypass `LocaleService.t()`.

**Consequences:** translators only edit CSV; scene files show keys in the editor
(by design). The lint tool treats runtime-composed prefixes (`stat.`,
`settings.`, `unlock.`, `plural.`, card `_where`/`_effect`) as used by
convention, so it still catches missing keys and ordinary unused rows. Fallback
strings in code are authoring aids only; lint fails if the key is absent.

## ADR-028 — Placeholder audio is synthesized WAV, 20 s loops (M5a)

**Status:** accepted (M5a)

**Context:** spec §9.9 names 60/90 s OGG loops and a concrete SFX list; M5a needs
audible, distinct placeholders without shipping licensed audio or requiring an
encoder in the toolchain.

**Decision:** `tools/generate_audio_placeholders.py` (bundled Python + numpy)
synthesizes three 20 s seamless loops and 30 SFX as 16-bit mono 44.1 kHz WAV in
`assets/audio/{music,ui,battle,meta}/`. `AudioService` addresses streams by id,
not by extension, so the final OGG files can replace the WAVs without touching
screens. Music players set `AudioStreamWAV.LOOP_FORWARD` at load time.

**Consequences:** the repository grows ~5 MB of placeholder audio; no gameplay
timing depends on track length. Before release, regenerate/replace with the
spec lengths and re-import; no code change is expected.

## ADR-029 — Modal screens via SceneRouter overlay, theme duplicate for text scale (M5a)

**Status:** accepted (M5a)

**Context:** the battle pause menu needs Settings without ending the run, and
100/115/130 % text size must apply live to a theme whose font sizes are authored
per type variation.

**Decision:** `SceneRouter.open_overlay(scene_id)` instantiates a screen on a
dedicated CanvasLayer above the running scene; `close_overlay()` frees it and
Android back closes it first. This is used for Settings from the pause menu;
normal navigation stays scene-based. `ThemeScaler` snapshots the authored font
sizes once, duplicates `main_theme.tres`, multiplies every type's font sizes and
assigns the duplicate to the Window. Battle HUD font overrides stay fixed so
combat numbers do not grow.

**Consequences:** overlays have no history entry; closing returns to the exact
frozen battle. Theme scaling is reversible and does not mutate the committed
`.tres`. A future overlay stack would need a small array instead of one slot.

## ADR-030 — Monetization stubs behind the spec §7.1 interfaces (M5b)

**Status:** accepted (M5b)

**Context:** M5b needs the shop and Speed Trial UI before M6 can add the AdMob
and Google Play Billing plugins. Shipping a half-wired store would either fake
purchases or leave broken buttons.

**Decision:** `AdsService` and `IapService` are autoload stubs with the exact
signals and methods from §7.1. `IapService.is_available()` is false, `query_products()`
returns the seven-product `IapCatalog`, and `purchase()` always emits
`purchase_failed(store_unavailable)`. The shop therefore shows `—` prices and
disabled "Store unavailable" buttons. `AdsService.show_rewarded()` logs the
placement, emits `rewarded_failed(stub_not_implemented)` and returns false; the
Speed Trial shows the localized "Ads arrive with M6" toast. A debug-only
`IapService.debug_simulate_purchase()` runs the real local path (RewardBundle ->
WalletService -> ownership -> `purchase_completed`) so the UI can be exercised.

**Consequences:** no release build can grant a purchase or reward for free; the
M6 adapters replace the stub bodies without touching screens. The debug purchase
button is compiled into debug builds only and must be removed/hidden when the
real store ships.

## ADR-031 — Leaderboard UI against LocalBackendStub behind one service seam (M5b)

**Status:** accepted (M5b)

**Context:** spec §6.7 requires weekly/all-time/tournament screens that work
offline until the M7 backend exists, and M7 must swap the implementation without
rewriting UI.

**Decision:** `LeaderboardService` (autoload) owns caching, the offline flag,
last-updated timestamps, own-rank insertion and reward tiers.
`LocalBackendStub` generates 50 deterministic names/waves around the player's
best and implements the §6.7 sort (wave desc, earlier submission, lower play
time). Screens never import the stub; the single M7 swap point is the marked
`_load()` call. The stub reports `is_offline() == true` so the banner is always
visible in M5b.

**Consequences:** the screen behaviour is fully testable headless and
deterministic for screenshots. M7 must preserve the response fields
(`id/nickname/avatar_id/best_wave/playtime/submitted_at`) and the sort contract.

## ADR-032 — One global toast channel with a pure FIFO queue (M5b)

**Status:** accepted (M5b)

**Context:** each screen had its own toast tween and node, so two services
firing together could overlap or replace each other; screens also duplicated
fade timing. Spec §4.12 asks for consistent feedback.

**Decision:** `ToastService` (autoload, CanvasLayer 110) owns one panel, one
tween and a pure `ToastQueue` FIFO. A new message waits until the visible one
finishes; consecutive duplicates are dropped. Screens call
`ToastService.show_toast(localized_text)` and keep their scene-local toast nodes
dormant for compatibility with existing scenes.

**Consequences:** message order is predictable and unit-tested; toasts survive
scene changes. Screens no longer control duration. A future modal-specific
message channel would need a separate queue.

## ADR-033 — Capture helper boots services before staging previews (M5b)

**Status:** accepted (M5b)

**Context:** `App` defers `init_services()`. Capture previously applied the
requested language and called `stage_preview()` before that deferred boot; the
boot then switched back to the saved language and refreshed live stats, so UK
and pseudo screenshots silently showed stale English defaults.

**Decision:** `tools/capture_scene.gd` calls `App.init_services()` (idempotent)
before applying the capture locale, pseudo flag and text scale, and calls the
scene's `stage_preview()` only after the scene has been in the tree for 0.2 s.

**Consequences:** captures reflect the requested locale and staged state. The
helper remains tooling-only and never writes settings back to `user://`.
